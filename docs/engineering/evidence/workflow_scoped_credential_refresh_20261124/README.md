# Scoped credential refresh for event workflows

The existing ConnectionService now offers explicit scoped refresh through the existing OAuthHandler and TaskOperationRecord arbiter. The synchronous scoped verification read remains read-only. Current active owner, role, exact connection/scope, encrypted grant, expiration and connection policy are frozen. The authorized provider endpoint/client material is frozen privately and only its keyed digest joins the operation request. An encrypted credential version keeps one attempt identity across policy/scope changes. Unknown outcomes never resend, including from a fresh OS process. Reconnects supply a new encrypted version.

A winning operation transition commits the encrypted replacement, safe AuditLog and receipt in one transaction, followed by fresh credential/authority/receipt readback. A peer reconnect, disablement, move or policy change wins over a stale refresh. Provider errors retain status/error class rather than private response bodies. Tokens, OAuth secrets and ciphertext are not placed in operation receipts, audit metadata, public responses or captured logs.

Source setup and actual callbacks use this path. The public callback test expires the enrolled grant, refreshes once through actual OAuthHandler with a controlled wire, reads the provider with the replacement, and admits one durable event; replay creates neither another subscription nor refresh. Unavailable credentials preserve the original enrollment effect: committed stays committed_unverified, uncertain stays effect_unknown. A still-valid grant remains usable when proactive refresh lacks material/configuration. Private read failures are safe503 outcomes. The picker explains credential waiting without automatically repeating setup.

The existing transition helper formerly committed a session-factory target write even when its conditional status update matched zero rows. A real scratch negative reproduced that on the prior published source. Losers now roll back; an optional trusted synchronous transition effect runs only after a winning CAS and before commit. During development, an ORM edit exposed missing flush before expiration of the identity map; that unpublished candidate was corrected and its negative retained. Another unpublished refresh candidate prematurely refused still-valid grants; the public callback negative and its passing twins are retained. No historical log was regenerated.

This is callback-triggered access-grant refresh, not subscription renewal or proactive maintenance. Original subscription lease expiry remains fixed; renewal, missed-event recovery, long-delayed setup and days-long qualification remain open. No new table/migration, token engine, application live-provider/model action, merge or deployment.

Patterns: [SQLAlchemy transaction framing](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html) and [Microsoft refresh-token lifecycle](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens). Renewal remains a separate requirement in [Graph lifecycle guidance](https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events).
