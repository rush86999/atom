## Engineering patterns that prevent repeated repair rounds

### Trace the whole request and every writer

Draw the actual path from authenticated entry to compiler or service, durable claim, effect, audit/readback, response projection and later consumer. Find every writer of the same row or JSON slot. A new CAS in one branch does not protect a legacy writer that still flushes by primary key.

Capture a real payload, durable row and response in scratch execution. Diagnose the first broken contract from that evidence. Read recent history before reintroducing removed compatibility behavior. Research primary documentation before introducing a genuinely new architecture; reuse established repo mechanisms first.

### Freeze intent and prove the actual result

Freeze server-owned authorized material before handlers, awaits or mutable callbacks. Returned fields cannot overwrite expected identity, scope, digest, operation or authority. A readable profile, matching title, point count, status boolean or self-reported digest is not material proof.

Maintain separate safe public projections and complete private verification inputs. Credential verification, source/version bindings, exact report content and provider material identity may require fields that must never be exposed publicly. Hiding a field from the UI does not justify omitting it from the verifier.

Use exact namespaced identities. An operation id cannot substitute for a message id; an invoice id cannot satisfy a PO id. Do not use substring, case-folding, punctuation removal or default-scope aliases to make an authority check pass. Preserve established explicit legacy policy only where the accepted contract permits it.

### Claim authority and material at the write boundary

A preflight read explains a refusal; a conditional write prevents the race. Bind the relevant actor authority, target revision/material, review generation and scope inside the transaction that owns the effect. Recheck assumptions at actual dispatch, not only at plan creation.

On SQLite, SELECT FOR UPDATE is not a sufficient concurrency fence. Use real guarded DML, existing uniqueness/FK constraints and a transaction that keeps the audit and local mutation atomic. A zero-match preserves the competing winner and rolls back the losing attempt. End stale snapshots before authoritative reload. Prevent dirty ORM state from issuing an unconditional update after a successful CAS.

Keep model calls, provider effects, file writes and unrelated callbacks out of retryable lifecycle mutation functions. A forced CAS retry must not execute the effect twice. Claim tokens or generations must prevent an expired worker's cleanup from releasing a newer reservation.

### Make uncertainty and idempotency explicit

Use these separate meanings consistently:

| State | Meaning | Recovery |
|---|---|---|
| Refused or not applied | No effect committed for this attempt | Refresh or correct the request; reuse the existing contract |
| Verified | Exact durable effect and evidence match | Continue dependent work |
| Already applied | Original operation is acknowledged, with its required proof | Do not dispatch again |
| Committed unverified | Commit is known, required readback is missing or refuted | Reconcile the original operation |
| Effect unknown | Commit or provider acceptance cannot yet be established | Preserve identity and reconcile; do not resend blindly |
| No change | No new effect was needed | Prove applicable current state without inventing a receipt |

A duplicate operation id is not proof of verified success. The same id with different material conflicts. A later revision must not be overwritten to make an old retry look current. Provider acceptance, Sent Items observation and recipient delivery remain distinct evidence stages.

### Generate complete negative matrices

For every binding, enumerate all required fields before testing. Exercise omission, null, empty, wrong type, wrong namespace and one-wrong-with-all-others-right, alongside complete valid twins. Do not rerun only the old seven probes when the verifier supplied a later twenty-case matrix.

For concurrency, place a deterministic second-session writer after validation and before the claim. Assert durable winner state, zero losing effects, preserved receipts, fresh-session behavior and the truthful response. Include both writer orders when rank or precedence matters.

Prefer execution-level counters and fresh-session reads over source-text assertions. Tests should reach real consumers, not only helper predicates. Keep health monitors, caches and provider cooldowns test-local so test order does not create empty candidate pools.

## Test and evidence delivery sequence

1. Reproduce the decisive failure or uncovered consumer boundary in scratch data. Push a clearly labelled reproduction checkpoint when useful; do not claim that a failing checkpoint is accepted.
2. Fix the shared contract and its parallel callers. Run the small failure-first matrix and valid twins until green.
3. Run the affected neighborhood once. Repeat only after a new change, failure or unresolved concern. Investigate an order failure or timing flake explicitly; do not keep rerunning until a clean count hides it.
4. Freeze the executed source. Restart only your own scratch processes when runtime changed, then capture the required API/UI/served boundary. Do not reuse a stale server as the repaired source.
5. Track exact original logs and artifacts. Verify source hashes against git show at the executed source and artifact hashes against the evidence commit. Then push the evidence and submit the exact refs.

Do not connect ad-hoc harnesses to the live dev database. Use TESTING=1 or an explicit unique scratch database/data/world path. A real migration test may use its own explicit pre-migration scratch DB as required by Alembic. Respect the external-drive world guard; never replace a missing symlink with an empty local world or reset an arbitrary existing directory. Stop only the processes/worlds you own.

A clean product source and an evidence-writing successor are different identities. Record both. If test-only successors or later harness changes exist, attribute the runtime and tests separately; do not relabel old runs as execution on the newer source. Corrections disclose superseded hashes and reasons, preserve original negatives, and never regenerate logs to fit a claim.

A submission includes the claim/routes, product and executed source, evidence ref, source/tree/build/world identity where applicable, exact commands, negative and positive results, unique-versus-overlapping counts, baseline exclusions, artifact hashes and remaining boundaries. Test-only commits do not close runtime findings against byte-identical code.

## Commit and push between coherent phases

Push to your own remote codex branch throughout the assignment, not only after the final report. A push is a backup and review checkpoint, not a request to stop. Continue directly to the next authorized phase.

| Checkpoint | Commit and push |
|---|---|
| Reproduction or contract test is stable | Push the scoped test/reproduction commit, clearly identifying any intentional red tests |
| Shared runtime fix passes the small gate | Push the implementation and relevant tests before starting the larger regression |
| Affected regression is complete | Push any actual fixes and the coherent tested checkpoint |
| Source is frozen and evidence verified | Push tracked logs/manifests and the final source/evidence index |

Use normal commits and pushes. On the first push use git push -u origin HEAD; subsequent pushes use git push origin HEAD. Inspect git status, the staged diff and branch first. Stage exact owned paths, not git add . or git add -A. Do not stage another agent's changes, secrets, live data, environments or generated junk. Review logs for sensitive material before tracking them.

Verify the push succeeded and local HEAD equals the remote tracking tip. A clean working tree does not prove a push occurred. Report a rejected or failed push truthfully with the local commit preserved; continue safe independent work while resolving the remote issue. Never force-push, delete another branch, rewrite shared history, merge protected main, deploy, or weaken checks to make a push convenient.

If another writer advanced the branch, inspect and coordinate before integrating. Prefer separate worktrees/branches and a normal reviewed merge of the intended changes; preserve source identities and rerun only affected checks. A WIP checkpoint is allowed when explicitly labelled incomplete and safe to publish; it must not be described as a passing candidate.
