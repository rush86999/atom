Keep three measurements separate:

- **Breadth:** which original functional promises have source-bound acceptance.

  model quality, security, compatibility and measured performance.

A high breadth score does not compensate for a broken teaching, authorization,
arithmetic or no-duplicate-effect boundary. A screenshot, registration count,
test-function count or successful refusal is not proof of working functionality.

## Verification required for each claim

Each claim row must lead to a specific assertion of user-visible behavior:

1. **Entry:** normal UI or supported authenticated public API, required profile,
   switches and actual served source/build. Mark standalone servers and direct
   service calls accurately; they do not prove ordinary app wiring.
2. **Positive:** unfamiliar inputs and independently known output or observable
   provider state. A deterministic substitute does not qualify a model-quality
   promise; a native canvas does not qualify Firecracker execution.
3. **Negative:** a nearby input that must refuse, clarify or reconcile. Assert
   no unintended mutation, calculation, learning or effect, not just an error label.
4. **Persistence:** new session/reload and real process restart when durable
   behavior is claimed; earlier completed work and operation identities survive.
5. **Concurrency/current authority:** when a boundary writes state or acts,
   exercise stale cached state, a writer after validation, duplicate submissions,
   revocation and uncertain post-effect failure as applicable.
6. **Consumption:** prove downstream code uses the output. Search must feed the
   employee; teaching must affect later appropriate work; approval must bind the
   dispatched payload; readback must verify the intended commercial state.
7. **Evidence:** executed commit/tree, configuration, exact command, expected
   values, actual results, retained failure record, tracked logs/artifacts and
   checksums verifiable with `git show`. No secrets or private customer content.
8. **Verdict:** implementation status and independent acceptance are separate.
   A changed consumer requires affected regression checks; unchanged consumers
   can retain historical evidence with recorded comparison. Do not rerun every
   campaign merely because documentation changed.

## Whole-product practical journeys

These journeys complement the feature count. Use one integrated candidate and
normal product interfaces for the final representative runs. Controlled provider
transport is valid evidence only at that stated level. Fresh external consent,
credentials, spend or effects require the corresponding authorization.

| Journey | Product outcome and discriminating controls | Lead |
|---|---|---|
| First use | Documented clean install, first login, employee creation, sample task, downloadable artifact; empty data and effective port/configuration paths work | Agent 1, Agent 2 launch support |
| Business knowledge | WorkDrive/OneDrive/Outlook or uploaded exports -> scoped ingestion/catalog -> relevant retrieval -> answer/work with citations; same-name ambiguity, stale/deleted/revoked source, pagination and partial coverage | Agent 2, Agent 1 consumer |
| Complex teaching | Teach method/mapping/format/context -> unfamiliar job -> exception -> correction while waiting -> old snapshot retained/new work corrected; wrong/missing context, conflicting/stale lessons, genuine downstream consumption | Agent 1 |
| Quote preparation | RFQ + customer identity + governing agreement + product/unit/pricing -> clarify material gaps -> exact quote/artifact -> reviewed or covered commercial update -> complete readback -> response draft | Agent 1, Agent 2 action boundary |
| Bookkeeping | Invoice + vendor/CoA/period evidence -> exact balanced proposal -> authorized write -> readback; duplicate identity, credit/partial payment, closed period, wrong entity and incomplete readback | Agent 2 |
| Long-running employee job | Independent branches, several waits, source/lesson changes, restart, deadlines/cost/active-work budgets, cancellation, revocation, duplicate reply and uncertain-effect reconciliation; no recreated completed work | Agent 1, Agent 2 provider faults |
| User-authored workspace app | Create three differently shaped canvases through guided UI -> validated typed state -> ordinary assignment -> governed action -> explicit teaching -> later work; forged values, stale edits, wrong target, restart and no duplicate | Both, shared-file ownership agreed |
| Planning and teams | Ordinary open-ended request -> useful persisted plan/specialists -> governed tool work -> verified outcome; no-progress recovery, task relevance, utility target and authority withdrawal | Agent 1 |

Industrial sales, services and a non-sales task must share the mechanisms without
domain-specific core code. Brennan is reference configuration, not a hardcoded
customer, accounting policy, provider requirement or embedded pricing assumption.

For long-running claims distinguish elapsed waiting from active work and genuine
recovery from budget correctness. Preserve already accepted two-hour evidence;
repeat elapsed runs only when changed scheduling/continuation behavior invalidates
it. Single-worker recovery, soak and multi-worker behavior are separate claims.
