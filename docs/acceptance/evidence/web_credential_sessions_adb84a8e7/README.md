# Credential-bound session repair

The native negative at9027c2c06 proved that a bearer issued before password recovery remained authorized afterward. The new source coordinates issuance and principal authorization with a versioned domain-separated HMAC of exact durable User identity and credential material. No raw password hash enters JWTs, and no new token store/table/schema is added. Current User queries refresh their identity-map state. Missing/unbound legacy claims require a fresh login; old refresh tokens cannot launder themselves into new authority. Refresh tokens are refused as access tokens.

Core login/register/refresh, OIDC issuance, shared mobile token paths, enterprise token producers/route consumers, core/shared WebSocket and device handshake readers use the same binding. Authenticated password changes also use exact credential/authority CAS, preserving a peer reset. Settings clears its old browser token and invokes existing sign-out on the explicit reauthentication response. This intentionally requires sign-in again after credential change and, when released, once for older unbound sessions. No live user was signed out during this work.

Reference: [Django session invalidation on password change](https://docs.djangoproject.com/en/5.2/topics/auth/default/#session-invalidation-on-password-change). Django documents the password-derived HMAC principle; this implementation adapts it to the existing signed-token architecture rather than introducing another session store.
