## AgentRadio for Atom — Implementation Plan

### What we're building
An async **lateral (peer-to-peer) messaging layer** that lets a fixed team of Atom agents coordinate in real time, modeled on the AgentRadio protocol from the VentureBeat article. Agents self-organize through 3 primitives instead of relying solely on top-down orchestration. This **complements** (doesn't replace) Atom's existing Conductor/Fleet/Queen orchestration, and ships **ON by default**.

**Scope (chosen defaults):** MVP lateral layer · Redis + in-memory transport · generic 4-agent coding team (Planner / Researcher / Implementer / Reviewer).

**Flag change per your direction:** `ATOM_LATERAL_MESSAGING_ENABLED` defaults to **`true`**. The layer is purely additive — new tables + 3 new tools + an optional thread auto-attached to fleets — so it cannot change existing orchestration behavior; agents simply gain the 3 tools. Safety rests on the protocol being timeout-bounded and queues only filling when another agent actually messages them, not on the flag.

---

### Phase 1 — Persistence layer (`backend/core/models.py` + Alembic)
Two new tables near `ChainLink` (`models.py:1811`), mirroring its shape and the `metadata_json` JSON-column pattern:

1. **`AgentThread`** (`agent_threads`) — `id`, `chain_id` (FK → `delegation_chains`, nullable), `name`, `created_by_agent_id` (FK → `agent_registry`), `status` (open/closed), `created_at`, `metadata_json`.
2. **`AgentMessage`** (`agent_messages`) — `id`, `thread_id` (FK → `agent_threads`), `from_agent_id`, `to_agent_id` (FK → `agent_registry`, nullable for broadcast), `content`, `mentions` (JSON list of mentioned agent IDs), `created_at`, `delivered` (bool), `metadata_json`.

Plus: add a nullable `thread_id` FK to **`AgentExecution`** (`models.py:991`), mirroring the existing `chain_id` FK at `:1001`.
- Alembic migration under `backend/alembic/versions/` (autogenerate + review), following existing naming/id conventions in that folder.

### Phase 2 — The message server (the core) — new `backend/core/lateral_messaging.py`
A singleton `LateralMessagingServer` mirroring the `FleetStateNotifier` Redis pattern (`distributed_blackboard_service.py`) + an in-process asyncio fallback:

- **In-memory backend** (default): `dict[thread_id, asyncio.Queue]` of `AgentMessage` + per-(thread, agent) `asyncio.Event`s for `wait_for_mention` blocking. Zero new infra — works in single-process dev/CI/tests.
- **Redis backend** (when `REDIS_URL`/`DRAGONFLY_URL`/`UPSTASH_REDIS_URL` set): pub/sub channel `lateral:thread:<thread_id>`, reusing `get_*_redis_url()` resolution exactly like `distributed_blackboard_service.py:109`. Cross-worker delivery. Same deadlock-prevention timeout pattern (`DEFAULT_LISTENER_TIMEOUT_SECONDS`) copied from the fleet listener.
- Public API (all `async`):
  - `create_thread(name, created_by_agent_id, member_agent_ids) -> AgentThread`
  - `send_message(thread_id, from_agent_id, content, mention_agent_ids=None) -> AgentMessage` — persists, pushes to queue(s), publishes to Redis channel.
  - `wait_for_mention(thread_id, agent_id, timeout) -> AgentMessage | None` — **blocks the calling ReAct loop** until a message mentioning `agent_id` arrives (drains the per-agent queue first to avoid lost messages), with timeout. Template: the `subscribe_to_fleet` listener (`distributed_blackboard_service.py:45-94`).
  - `get_thread_history(thread_id) -> List[AgentMessage]`
- Singleton accessor `get_lateral_messaging_server()` like `get_fleet_state_notifier()`.
- Feature-flag-aware: reads `ATOM_LATERAL_MESSAGING_ENABLED` (default **true**). Tools still gracefully degrade (return a clear "disabled" note) only if an operator explicitly sets it `false`.

### Phase 3 — Agent-callable tools — new `backend/tools/agent_messaging_tool.py`
Mirror `memory_tool.py` exactly (async funcs + `register_agent_messaging_tool(registry)` helper). Three async functions wrapping the server:
- `create_thread(name, member_agent_ids, **kwargs)` — complexity 2, `INTERN+`.
- `send_message(thread_id, content, mention_agent_ids=None, **kwargs)` — complexity 2, `INTERN+`.
- `wait_for_mention(thread_id, timeout=120, **kwargs)` — complexity 1, `INTERN+`. Returns the message or a timeout note (never raises).

Wire-in (2 spots):
1. `tools/registry.py`: add `_register_agent_messaging_tools()` calling `register_agent_messaging_tool(self)`, and call it from `initialize()` (`:390`, alongside the existing `_register_*` calls at `:402-413`).
2. `core/atom_meta_agent.py`: add the 3 names to `CORE_TOOLS_NAMES` (`:351`) so the ReAct loop exposes them.

### Phase 4 — Auto-wire threads into Fleet recruitment
In `_recruit_fleet` (`atom_meta_agent.py:1498`), after the `DelegationChain` + `ChainLink`s are created (`chain.id` at `:1541`), auto-create one shared `AgentThread` scoped to the chain and stamp its `thread_id` onto each recruited agent's execution context (and the new `AgentExecution.thread_id`). Gives a fixed team a lateral channel for free, with the chain as the team scope — structurally matching the article's fixed-4-agent-team setup.

### Phase 5 — Reference 4-agent coding team config — new `config/lateral_teams/coding_team.yaml`
A declarative team definition (mirrors Atom's existing YAML config style in `config/`): 4 roles (Planner / Researcher / Implementer / Reviewer), each with a system-prompt snippet describing when to `@mention` peers. Faithful port of the article's team. Loaded by a small loader so teams are swappable later.

### Phase 6 — Tests
Following Atom's quality bar (tests pass 100%, coverage ≥70%):
- Unit: `backend/tests/unit/agents/test_lateral_messaging.py` — server in-memory backend (create/send/wait/timeout/mention routing), with Redis paths mocked.
- Unit: `backend/tests/unit/agents/test_agent_messaging_tool.py` — tool wrappers, governance flags, explicit-disabled behavior.
- Integration: a 2-agent ping-pong that proves `wait_for_mention` actually unblocks across `asyncio.create_task` agents (proves the harness works).
- Mirror patterns in `backend/tests/unit/agents/`.

### Phase 7 — Docs
- `docs/agents/lateral-messaging.md` — architecture, the protocol philosophy ("let LLMs figure out coordination"), the 3 primitives, team config, env flags. Note the article's ~10× cost trade-off as a known consideration.
- Short entry in `docs/agents/overview.md` linking to it.
- Add `ATOM_LATERAL_MESSAGING_ENABLED` (default `true`) to `docs/reference/ENVIRONMENT_VARIABLES.md` and `.env.example`.

---

### Explicitly NOT in this MVP (to keep scope tight)
- No UI/observability view yet.
- No cost-guard / budget auto-throttle (flagged as a known trade-off in docs).
- No benchmark harness (the "62% vs 32%" reproduction is a separate scope).
- No changes to existing Conductor/Queen/Fleet behavior — purely additive.
