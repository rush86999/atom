# Plan: Code-Interpreter Data Analysis Tool for Agents

A new agent tool that runs pandas/DuckDB/sklearn code inside atom's existing sandbox runtime, enabling autonomous data analysis, forecasting, and predictive modeling for business automation workflows.

## Evidence validation (each feature needs ≥2 independent sources)

### Feature 1: Code-interpreter tool (pandas/DuckDB in sandbox) — ✅ VALIDATED
- [DABstep benchmark (arXiv 2506.23719)](https://arxiv.org/html/2506.23719v1): 450+ multi-step data analysis tasks; even top agents achieve only 14.55% on hardest tasks → code-interpreter approach is the SOTA pattern for multi-step analysis.
- [DS-STAR (Google Research, 2025)](https://research.google/blog/ds-star-a-state-of-the-art-versatile-data-science-agent/): raised DABstep accuracy from 41%→45% using code execution + self-debugging.
- [DuckDB vs Pandas benchmarks (codecentric)](https://www.codecentric.de/en/knowledge-hub/blog/duckdb-vs-dataframe-libraries): DuckDB consistently outperforms pandas on large analytical workloads, handles larger-than-RAM datasets.
- [DuckDB official benchmarks](https://duckdb.org/2024/06/26/benchmarks-over-time.html): 3-25× faster, 10× larger datasets on same hardware.
- [monty-data-agent (GitHub)](https://github.com/EvanOman/monty-data-agent): production reference for DuckDB-as-agent-brain pattern.
- [Modal: sandbox as tool](https://modal.com/resources/best-code-execution-sandboxes-tool-calling-ai-agents): sandboxed code execution is the SOTA pattern for tool-calling agents.

### Feature 2: Predictive modeling tools (forecast, regress) — ⚠️ RESTRICTED
- [IBM Developer: agentic ML with pre-trained models](https://developer.ibm.com/articles/agentic-ml-tasks/): use classical ML (sklearn) via tool-calling, not raw LLM forecasting.
- [AWS: predictive ML models with MCP](https://aws.amazon.com/blogs/machine-learning/enhance-ai-agents-using-predictive-ml-models-with-amazon-sagemaker-ai-and-model-context-protocol-mcp/): demand forecasting via agent + classical ML.
- [Towards Data Science: classical ML for AI agents](https://towardsdatascience.com/using-classical-ml-to-empower-ai-agents/): LLMs orchestrate sklearn tools; they don't forecast natively.
- [DeepLearning.AI community](https://community.deeplearning.ai/t/use-of-llm-for-any-forecasting-scenarios/690668): critical reminder — LLMs predict tokens, not numbers. Must use sklearn/statsmodels via tool-calling.
- [arXiv 2605.09252](https://arxiv.org/html/2605.09252v1): LLM agents call tools indiscriminately — needs governance gating.

**Restriction:** Predictive modeling tools require SUPERVISED maturity minimum. Financial forecasting results must pass through HITL before being acted upon. The LLM generates the modeling code; the sandbox runs it; results are surfaced for human review before deployment.

### Feature 3: Dataset management (load/cache/reference) — ✅ VALIDATED
- [ExperiencedDevs consensus](https://www.reddit.com/r/ExperiencedDevs/comments/1lvlvw3/): LLMs should NOT ingest raw large files into context. Orchestrate via code instead.
- [n8n community](https://community.n8n.io/t/editing-excel-data-using-llms/158373): same conclusion — pre-process data, don't feed raw to LLM.
- [DuckDB Lab: DuckDB as agent brain](https://duckdblab.org/en/post/duckdb-ai-agent-brain/): dataset referenced by name across turns; DuckDB holds the connection.

### Security (sandbox code execution) — ✅ ATOM ALREADY HAS THIS
- [Modal: run untrusted code safely](https://modal.com/resources/run-untrusted-code-safely): sandboxing essential; without it, system compromise/data exfiltration/lateral movement.
- [Trend Micro: AI agent code execution vulnerabilities](https://www.trendmicro.com/vinfo/us/security/news/cybercrime-and-digital-threats/unveiling-ai-agent-vulnerabilities-code-execution): systemic risks; need filesystem/network isolation.
- [arXiv 2504.00018](https://arxiv.org/html/2504.00018v1): academic paper on risks of executing LLM-generated code.
- **Atom already has:** Docker/E2B/Firecracker sandbox with AST tripwires, egress proxy, resource caps, network isolation. This is the hardest infrastructure piece and it's already built.

## Architecture

### New file: `backend/tools/data_analysis_tool.py`

A tool registered with the agent tool registry that:
1. Accepts a natural-language analysis request + optional dataset reference
2. Generates Python code (pandas/DuckDB/sklearn) via the LLM
3. Executes it in the existing sandbox runtime (`core/sandbox_runtime/`)
4. Returns structured results (tables, statistics, charts)
5. Optionally renders results to Canvas sheets

### Tool functions exposed to agents:

| Tool | What it does | Maturity gate |
|------|-------------|---------------|
| `analyze_data` | Load a dataset (CSV/Excel/JSON/SQL), run analysis code in sandbox, return results | INTERN |
| `load_dataset` | Load and cache a dataset by name for cross-turn reference | INTERN |
| `forecast` | Time-series forecasting (statsmodels/prophet-style) via sandbox | SUPERVISED |
| `run_model` | Regression/classification (sklearn) via sandbox | SUPERVISED |

### Dataset manager: `backend/core/data/dataset_manager.py`

Manages loaded datasets across agent turns:
- `load(source, name)` — loads CSV/Excel/JSON/DB into a DuckDB in-memory connection, returns a handle
- `get(name)` — returns the cached dataset connection
- `query(name, sql)` — runs SQL against the cached dataset
- Datasets are tenant-scoped and session-scoped (cleared on session end)
- DuckDB handles out-of-core datasets (larger than RAM) per the benchmarks

### Sandbox integration

The tool uses the existing `core/sandbox_runtime/` infrastructure:
- `get_runtime()` → selects Docker/E2B/Firecracker (already built)
- `SandboxPolicy` with `max_exec_seconds=30` (data analysis needs more time than code verification's 15s)
- Data passed via `inputs=` dict (becomes module-level globals in the sandbox)
- The sandbox image needs pandas + duckdb + scikit-learn + statsmodels pre-installed (Docker image update)
- AST tripwires + egress proxy already protect against data exfiltration

### Canvas integration

Analysis results can be rendered to Canvas sheets via the existing `present_sheets_canvas` tool:
- The `analyze_data` tool returns results as a dict
- The agent can then call `present_sheets_canvas` to push a table to the UI
- Or `present_chart` for visualizations (matplotlib figure → base64 → Canvas chart)

## Build order

### Phase 1: Dataset manager + code-interpreter tool (the foundation)
1. `core/data/dataset_manager.py` — DuckDB-backed dataset loading/caching/querying
2. `tools/data_analysis_tool.py` — `analyze_data` + `load_dataset` tools registered with the agent
3. Sandbox integration — execute generated pandas/DuckDB code in the existing sandbox
4. Tests — dataset loading, query execution, code-interpreter flow, error handling

### Phase 2: Predictive modeling tools (governed)
1. `forecast` tool — time-series forecasting via statsmodels in sandbox
2. `run_model` tool — regression/classification via sklearn in sandbox
3. Governance gating — SUPERVISED maturity minimum; HITL for financial forecasts
4. Tests — forecasting accuracy, model training, governance gate enforcement

### Phase 3: Canvas rendering + documentation
1. `present_analysis` helper — render analysis results to Canvas sheets/charts
2. `docs/architecture/DATA_ANALYSIS.md` — architecture, evidence basis, security
3. README update — new feature in Key Features section

## Out of scope (evidence-based exclusions)
- **Native LLM forecasting** — [DeepLearning.AI community](https://community.deeplearning.ai/t/use-of-llm-for-any-forecasting-scenarios/690668): LLMs predict tokens, not numbers. Must use classical ML via tool-calling.
- **Raw Excel cell manipulation** — [ExperiencedDevs](https://www.reddit.com/r/ExperiencedDevs/comments/1lvlvw3/): LLMs should orchestrate code, not edit cells directly. Canvas sheets already handles the UI.
- **Real-time streaming analytics** — separate infrastructure effort (Kafka/Flink). Not needed for business automation batch analysis.
