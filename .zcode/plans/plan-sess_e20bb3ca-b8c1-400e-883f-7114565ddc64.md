# Restructure: CODE as a 2-stage reconcile→execute pipeline

## Correction
`_reconcile_branch_conflicts` is for **coding** — it merges divergent coding-agent action dicts (e.g. `{"action":"read","target":"db.py","status":"ok"}`). I incorrectly positioned it as the generic VOTING fallback. Per the chosen approach, CODE verification should be a **2-stage pipeline**: reconcile (merge divergent action dicts) → execute (verify code correctness in sandbox).

## Design

Add a `CODE_PIPELINE` strategy implemented by a `CodePipelineVerifier` that composes the two existing verifiers:

```
candidates (coding-agent outputs: action dicts and/or code)
   │
   ├─ Stage 1 — RECONCILE (VotingVerifier.reconcile_only_sync)
   │    merge divergent action dicts via per-key frequency vote
   │    → merged_candidate (or majority winner if all-distinct non-dicts)
   │
   ├─ Stage 2 — EXECUTE (ExecutionVerifier)
   │    extract code from merged_candidate (code/source/output keys)
   │    if code found → run in sandbox against tests spec
   │      passes → return merged_candidate (verified)           ✓
   │      fails  → winner=None (→ orchestrator voting fallback)
   │    if no code found → return merged_candidate (reconciled, execution n/a)
   │
   └─ result carries both stages' details for observability
```

The pipeline degrades gracefully at each stage:
- Reconcile produces nothing (non-dict candidates, all distinct) → use majority winner → proceed to execute.
- No code in the result (pure action plan, e.g. `{"action":"read",...}`) → skip execution, return reconciled result. This preserves the original reconciler behavior for coordination-only steps.
- Sandbox unavailable → execution stage returns "skipped", reconciled result still returned (reconcile-only is still valuable).
- Code present but fails tests → `winner=None` → orchestrator's universal voting fallback. This is the new correctness gate the original reconciler lacked.

### `backend/core/orchestration/verification/code_pipeline.py` (NEW)
- `CodePipelineVerifier(Verifier)` with `strategy = VerificationStrategy.CODE_PIPELINE`.
- Constructor takes optional `sandbox_runtime` (passed through to the internal `ExecutionVerifier`) and optional `voting_verifier` / `execution_verifier` for test injection.
- `verify()`:
  1. Runs `VotingVerifier` majority+reconcile to get a merged candidate (reuse the existing verifier, not just `reconcile_only`, so we get the majority short-circuit too).
  2. Extracts code from the winner via `ExecutionVerifier._extract_code`.
  3. If code found: runs `ExecutionVerifier` on just that winner (single-candidate verify). If it passes → return the winner with both stages' details. If it fails → return `winner=None` with the failure reason.
  4. If no code found → return the reconciled winner (stage 2 is n/a).
- `details` includes `{"stage_1": {...}, "stage_2": {...}}` so callers see what each stage did.

## What stays unchanged
- `VOTING` strategy keeps majority + reconcile bundled (backward compat for UNKNOWN/PLANNING — byte-identical behavior, all existing tests pass).
- `EXECUTION` stays as a standalone strategy (still useful for pure-code tasks without coordination).
- `_reconcile_branch_conflicts` shim in conductor_agent.py unchanged (still delegates to `VotingVerifier.reconcile_only`).
- All other strategies (SCHEMA, FORMAL, GROUNDED, JUDGE) unchanged.
- The universal voting fallback on `winner=None` still applies (so a failed execution gate falls through to voting).

## Behavior preservation
- UNKNOWN → VOTING (unchanged).
- CODE was EXECUTION → now CODE_PIPELINE (reconcile→execute). This is the intended correction. The conductor integration test updates to match.
- All 117 existing verification tests pass; only the 2 CODE-routing assertions change (CODE→CODE_PIPELINE instead of CODE→EXECUTION).
